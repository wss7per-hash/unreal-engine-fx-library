# FXLibraryClient 深度评测报告

> 评测视角：**产品经理 + 系统/架构审视**。
> 方法：逐文件精读 `app/`（`main_window.py` 2739 行、`asset_grid.py`、`scanner.py`、`database.py`、`ue_bridge.py`、`ue_export.py`、`uasset_thumb.py`、`config.py`、`models.py`、`style.py`、`i18n.py`）+ 对照 `UI_AUDIT_REPORT.md` + 实际 `tools/qa_audit.py`。
> 日期：2026-07-23

---

## 〇、一句话结论

**工程质量很高**（QA 全过、UI token 化规范、主题/对比度旧债基本清干净、纯视觉与基础交互已过关）。但站在"能不能真的用、用得安不安全"的角度，存在三类会致残的问题：

1. **架构级可扩展性缺陷** —— 对真实 UE 工程（成千上万个 `.uasset`）直接不可用或卡死；
2. **数据完整性缺陷** —— 重新扫描会静默抹掉用户的标签/收藏/评分，且误判即静默删资产；
3. **核心闭环名实不符** —— 头牌的"导出 .fxpack""健康扫描""UE 真实渲染"都没真正打通。

下面按严重度分层。**标「新发现」的条目是 7/22 UI 审计未覆盖、本次深评才暴露的。**

---

## 一、🔴 致命级 · 架构与数据完整性（建议 P0）

### ①【新发现】网格零虚拟化 —— 真实库规模下直接卡死/OOM
- `AssetGrid.set_assets()`（`asset_grid.py:566`）对每个资产 `AssetCard(a, ...)` 新建一个 QWidget（内含 2 个 QLabel + 2 个 QPushButton + 多层 layout）。
- `_relayout()` 用 `QGridLayout` 把**全部卡片一次性摆放**，无任何回收/懒加载/虚拟滚动。
- 后果：扫描一个 UE `Content` 目录往往有 **1 万～10 万+** `.uasset`。实例化数万个 QWidget ⇒ Qt 布局引擎卡死、内存爆掉、应用假死。
- 7/22 审计把它降格成"搜索卡顿 (P1-K)"，这是**严重低估**——它不是体验问题，是"产品不可用"的硬墙。
- **修复方向**：改用 `QListView` + 自定义 `QAbstractItemModel`/`QStyledItemDelegate` 做虚拟滚动；或至少卡片复用 + 只实例化视口内卡片。

### ②【新发现】重新扫描会抹掉用户全部标签/收藏/评分/备注
- `ScannerWorker.run()`（`scanner.py:318`）每次都 `a = FXAsset(source_path=f, name=..., ...)` 重建对象，**不携带 `tags/favorite/rating/note`**（取默认值 `""/False/0/""`）。
- 随后 `db.upsert_asset(a)` → `INSERT OR REPLACE`（`database.py:230`）**整行覆盖**。
- 后果：用户辛苦打的标签、收藏、评分、备注，**只要再扫一次（含启动时的自动扫描 `_auto_scan`），全部归零**。这是实打实的数据丢失 bug。
- **修复方向**：`upsert` 改为"只更新扫描可得字段（type/size/thumb/tier/has_thumb），保留用户字段"，或写入前先 `get_asset` 合并旧 tags/fav/rating/note。

### ③【新发现】扫描遇单个文件异常 → 整个导入 abort
- `scanner.py:332`：`except Exception as e: self.failed.emit(...); return` 写在 `for f in files` **循环体内**。
- 后果：目录树里**任意一个**文件抛异常（权限锁、编码边角、解码意外）→ 整个扫描立刻 `return`，库只建了一半，且**无续扫/无断点**。对大目录这是"几乎必然触发"。
- **修复方向**：把 `try/except` 下沉到单文件粒度，`failed` 改为收集 `errors` 列表、继续处理其余文件，结束汇报。

### ④【新发现】fx_only 模式静默 DELETE 资产 —— 误判即丢数据
- `scanner.py:260`：`if fx_only and t == TYPE_UNKNOWN: db.delete_asset(f)` —— 只要类型启发式判成 Unknown，就直接从库里删。
- 启发式 `detect_type_offline` 只 `read(8*1024*1024)`（前 8MB）做子串匹配；包名表在 8MB 之后的大资产、或标记被压缩的资产会被误判 Unknown ⇒ **被悄悄删除**。
- **修复方向**：Unknown 不要删库，标记为"未分类"保留；类型识别失败应保守而非破坏性。

## 二、🟠 高风险 · 数据安全 / 性能（建议 P1）

### ⑤【新发现】SQLite 无 WAL、无备份；库路径可指向网络/USB
- `database.py` 用裸 `sqlite3.connect(path)`，默认 rollback journal、`autocommit` 关闭、每写即 commit。无 `PRAGMA journal_mode=WAL`、无 `synchronous` 策略、无自动备份。
- `config.library_dir` 可被用户指向任意路径（含网络盘/移动盘）。扫描中途崩溃 ⇒ 单文件损坏风险高于 WAL 模式。
- **修复方向**：开 WAL；启动时对 `.db` 做时间戳备份；校验文件可写。

### ⑥【新发现】任何小操作都触发全库重读 + 全网格重建
- `_trash_assets` / 标 tag / 切收藏视图 / 还原回收站 … 全部走 `_reload_library()`（`main_window.py:1734`）→ `db.get_assets()` **全表读出** → 重建 `self._all_assets` 全量列表 → `_apply_filters` → `grid.set_assets` 全量拆建。
- 大库下**每点一下都卡一次**（叠加 ① 更致命）。
- **修复方向**：局部更新（只增删改变动行 + 增量刷新对应卡片），不要动不动全量 reload。

### ⑦【已知·重申】搜索无防抖 + 每次整网格重建
- `_apply_filters` 在 `search.textChanged` 上无 debounce，每敲一字就 `grid.set_assets` 全量重建（见 ①）。QA 只测 4 张卡片所以无感。
- **修复方向**：250ms 输入防抖 + ① 的虚拟滚动。

### ⑧【新发现】"永久删除"名实不符 + copy 模式孤儿文件泄漏
- `_permanently_delete_selected`（`main_window.py:2719`）只 `db.permanently_delete_asset`（删 DB 行），**不动磁盘上真实的 `.uasset`**。即"永久删除"其实是"从目录里遗忘"，文件还在。用户可能以为清了磁盘其实没清。
- 更隐蔽：在 `copy` 导入模式下，文件被复制到 `library/files/`，之后无论怎么"删除"都**永不清理** ⇒ 孤儿文件只增不减、磁盘泄漏。
- **修复方向**：要么"删除"真把磁盘文件移入系统回收站（带确认），要么明确改名"从目录移除"并补 `library/files` 清理；copy 模式需有孤儿回收机制。

### ⑨【已知·重申】UE 渲染若是真路径，会逐个资产冷启动 UnrealEditor
- 即便接上 `_auto_render_thumbs`（当前 0 调用死代码），每个资产一次完整编辑器冷启动（30–90s），无批处理合并。批量渲染会慢到不能忍。
- **修复方向**：一次 UE 进程内循环渲染多资产；或用 `-ExecutePythonScript` 批量命令。

## 三、🟠 产品级 · 名实不符 / 功能缺口（汇总自 7/22 审计 + 复核）

> 以下 ⑩⑪⑫⑬ 在 `UI_AUDIT_REPORT.md` 已详述，此处仅汇总，证明"核心闭环自洽性"问题仍在。

- **⑩ 导出 .fxpack 完全缺失**：只能"导入"别人给的包，**产不出**自己的包。设计文档 MVP 第 2 条（递归依赖 + manifest + 缩略图打包）至今无 UI 入口。产品"库/复用/分享"飞轮从第一步断。
- **⑪ 资产健康扫描（模块 E）从未接入 UI**：`health` 字段恒为 `"ok"`，用户永远看不到。`fx_health.py`/DB/`i18n` 都备好了，但无按钮、检查器无"健康"行。
- **⑫ "播放 / UE 真实渲染缩略图"名实不符**：右键文案承诺"生成**播放**缩略图 / UE 渲染真实帧"，实际 `_gen_embedded_thumb` 只做静态内嵌读取（tier 1）或占位（tier 4），**从不启动 UE**；真正的 `_auto_render_thumbs` 全代码零调用。
- **⑬ "导出到 UE 工程"实为复制文件**：`ue_export.export_to_ue_project` 只是把 `.uasset` 拷进用户选的 Content 文件夹，不注册进实时工程；叠加 ⑩，整个"导出"叙事自相矛盾。

## 四、🔵 正确性 bug（上一轮修复引入 / 固有）

### ⑭【新发现】详细信息表排序后「行 ↔ 数据」错位
- 上一轮为表格开了 `setSortingEnabled(True)`。Qt 排序只移动**视觉行**，`self._details_assets` 列表顺序不变。
- `_on_details_current_changed`（currentRowChanged）用 `a = self._details_assets[item.row()]` 取资产 ⇒ **排序后点击会打开错误的资产**进 Inspector。
- **修复方向**：排序后改用 `self.details_table.item(row,0).data(Qt.UserRole)` 反查 source_path，再 `db.get_asset` / 在 `_details_assets` 里按 path 定位。

### ⑮【已知】两个"设置"入口行为分歧
- 库菜单 `_open_settings`（`:474`）改了 `library_dir` 会 `_open_db()` 重开库；齿轮 `_settings` 路径则不一定。改库目录一处方生效一方不生效。应合并为同一实现。

## 五、缺陷优先级 & 修复顺序建议

| 级 | 编号 | 问题 | 影响面 | 修复成本 |
|---|---|---|---|---|
| **P0** | ① | 网格零虚拟化 | 真实库规模不可用/OOM | 高（架构改造） |
| **P0** | ② | 重扫抹掉用户标签/收藏/评分 | 静默数据丢失 | 低（改 upsert 语义） |
| **P0** | ③ | 单文件异常 abort 整轮扫描 | 库半截、无续扫 | 低（except 下沉） |
| **P0** | ④ | Unknown 资产被静默 DELETE | 误判即丢资产 | 低（改保留策略） |
| **P1** | ⑭ | 详情表排序后错位 | 点错资产 | 低 |
| **P1** | ⑤ | DB 无 WAL/备份 | 崩溃易损 | 低 |
| **P1** | ⑥ | 任意小操作全量 reload | 大库卡顿 | 中 |
| **P1** | ⑩ | 导出 .fxpack 缺失 | 核心闭环断 | 中 |
| **P1** | ⑪ | 健康扫描未接 UI | 卖点失效 | 中 |
| **P1** | ⑫ | 缩略图 UE 渲染名实不符 | 误导 | 低（接上或改文案） |
| **P2** | ⑦⑧⑨⑬⑮ | 搜索防抖 / 删除名实 / 渲染批处理 / 导出改名 / 设置合并 | 体验+清晰度 | 低~中 |

**建议先把 ②③④⑤ 这四件「低成本高杀伤」一次修掉**（合计代码量很小，却直接消除数据丢失与库损坏风险），再投入 ① 的虚拟滚动架构改造，最后补 ⑩⑪⑫ 的产品闭环。

## 六、一句话总结

> 这软件"长得好看、基础交互顺"，但**在规模、健壮性和数据完整性上是脆弱的**：用它在真实 UE 工程上扫一次，要么卡死，要么把你辛苦标的标签冲掉，要么因为一个怪文件把整轮扫描搞崩。把它当成"个人小库（几百个资产）的漂亮管理器"完全合格；要当成"团队可依赖的特效资产中枢"，先把 ①②③④ 这四道坎过了再说。
